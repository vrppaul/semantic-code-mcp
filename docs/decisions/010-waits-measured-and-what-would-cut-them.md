## Decision (proposed)

Each change is built with the phases split before and after, on an idle machine, in alternating turns, as ADR 009's measurements were; the figures above are what it is held to.

### O1. Watch the files instead of scanning them before every search

The server keeps a watcher of each project's files (`watchfiles`, Rust's notify: inotify, FSEvents, Windows' own), and a search's stale check reads its queue of changes: the work of the changes alone, under a millisecond. A full scan stays for the first use, a queue that overflowed, and now and then as a check. Expected: a warm search on Sentry about 40 ms instead of 340, `index_status` about 5 ms, a search after an edit about 100 ms. It costs a dependency (the owner's word first), Linux's limit of inotify watches, and the care missed events, renamed directories and a checkout of thousands of files need. A change of principle: less work, not the same work faster.

Built on watchfiles (`15901da`, 2026-10-29, on the owner's word for the dependency) and reverted (`b183058`) after its review (REJECT). It was faster (Sentry: `index_status` 34-36 ms against 148-152, a warm search 111-116 against 194-243, a fresh server's first answer 0.2 s slower) and wrong:
- every search failed on a project with one directory name that is not UTF-8 (`RustNotify` raised on its path and nothing caught it);
- edits were lost when reads filled inotify's queue: notify 8 asks for an event at every file opened (`IN_OPEN`), one `rg` over Sentry queued 27,905 events against a queue of 16,384, and watchfiles drops the overflow, which carries no path, so a read named fewer than 1,000 paths and was trusted (two `rg` at once lost 2 edits of 10, six lost 9);
- a directory made while the watcher started was never watched, as the directories were listed before the watches existed;
- `git ls-files --others --ignored --directory` names a directory whose files are all ignored though the directory is not (`git check-ignore` says so), and such a directory went unwatched (the committed property failed with `--hypothesis-seed=1`);
- a linked worktree's index lies outside `.git`, a file; a link's target outside what is watched was not followed, as the construction said it would be; a root made again and a nested repository's `.git` removed sent nothing the watcher kept;
- every git command that rewrites the index made the next look a full scan and a new watcher of 3,132 directories, 227 ms against the 91 a scan cost, as `RustNotify` adds no watch to a live watcher;
- tests could not fail with its 1,000-path rule, the submodule rule or the registry's close broken, and no end-to-end test ran the default setting.

`RustNotify` gives no mask, no overflow and no watch added to a live watcher, so none of the second, third and sixth could be fixed within it. Built again on Linux (2026-10-29), on the owner's word, by the construction the review's step back drew, with what building it settled; `services/files.py` says how it works and `watching/inotify.py` holds inotify's calls:
- **inotify read directly** through `ctypes`, nothing to install: one instance per project, its descriptor non-blocking and read to its end at each look. The kernel queues an event inside the call that changed the file, so a look holds every change made before it: no thread, no markers, no deadline.
- **A mask of changes alone** (`IN_CREATE`, `IN_DELETE`, `IN_MODIFY`, `IN_CLOSE_WRITE`, `IN_ATTRIB`, `IN_MOVED_FROM`, `IN_MOVED_TO`, `IN_DELETE_SELF`, `IN_MOVE_SELF`), never `IN_OPEN` or `IN_ACCESS`: reading every file queues nothing. A queue that overflowed starts the following again.
- **Watched, then listed**: each directory's watch is added before its entries are read; a new directory gets its watch on the live instance and is listed, with no restart; the directories gone in one look, deleted or moved, are forgotten in one pass, their watches and those below dropped and their files read again (one pass a directory took 1.7 s on Sentry for a tree of 599 deleted, its review found). A walk pending is never dropped: a gone path fails its watch, so two directories swapped in one call are both followed.
- **Git's listing asked again, never patched**: the files git listed are kept as its last answer; a path that changed is read again by the scan's rules; a name git has not listed made in a directory followed, or git's index rewritten (`git add`, a commit, a checkout, a `git status` that refreshes it), asks git for its listing again, git's part of a scan alone (45 ms on Sentry), and the paths whose listing changed are read again with the rest; never a new watcher. Asking `git check-ignore` of each new name instead, 4 ms against 45, kept a copy of the listing patched path by path, and its review found a listing taken in a burst losing an index change that landed meanwhile. Git's own directories are found by `git rev-parse --git-dir --git-common-dir`, so a linked worktree's index, excludes and configuration are watched where they lie.
- **Directories pruned only where git ignores them whole**: `git ls-files --ignored --directory` names them, and also a directory whose every file it ignores though not the directory, so `git check-ignore` confirms each of those a walk would enter; asking it of every directory, a level at a time, cost a second on Sentry. It is asked again once every directory is watched: a `.gitignore` changed between, in a directory not yet watched, sent no event, so a changed answer starts the following again. A directory a pattern covers, or whose name is not UTF-8, is not watched, as the scan keeps none of its files.
- **A nested repository as git reads it**: git looks into a directory holding a repository of its own only where it tracks files below it, so `git ls-files --cached` is asked of each one a walk meets; the others are watched alone, for their `.git`. Whatever git's listing says of it since holds, as every name made in it or index rewritten asks git again; git coming to look into one, which only a checkout or git's plumbing makes, is the check against a scan's to find.
- **What changes the rules starts again**: a `.gitignore`, an excludes file, git's `info` or configuration (`config`, a worktree's `config.worktree`, where `core.excludesFile` may be set), a `.git` made or gone (a nested repository's, the project's own; submodules added or made active write the configuration), a queue that overflowed, and the root or git's own directories no longer where they were (a `stat` of each at every look, as a directory above one moved, a linked worktree's main repository, sends its watches nothing): a fresh start, its walk and a full scan.
- **Read at every look what no watch's events tell**: a symlink git lists, whose target may lie anywhere, a file of more than one name, which an edit through its other name changes with no event here, and a file git lists in a directory nothing follows (one git ignores though it tracks the file, one a nested repository holds, one the server may not read): the scan's own reading, of a few files. A link's target's directory watched instead, as the review's step back drew it, would miss a chain of links and a target where nothing else is watched.
- **Elsewhere a scan at each search**: a file system whose changes another machine makes (a network share, FUSE, WSL's mount of Windows' drives), the root's or one mounted below it, by its type in `/proc/self/mountinfo`; a directory outside a repository, or below a repository's root (a home under git), where directories outside the project decide what git lists; a project with submodules, whose own indexes decide their files; wherever the system fails a following (inotify's limits of watches or instances, an error reading a directory), for the rest of the session; and wherever `SEMANTIC_CODE_MCP_WATCH_FILES=false`.
- **Checked against a scan every 5 minutes**: what no event tells, the user's global git configuration and excludes file, a second name a file got after it was read, a file system mounted over a directory followed, is then seen within that time; a difference is logged as a warning, counted and named, and the following starts again from the scan. A forced index run starts the following again too. Its review asked for this net once each rule it could reach was in place: an unknown miss becomes minutes of staleness and a line in the log, not a session's.
- **Tests that can fail**: the property that the files followed are those a scan finds, over random changes in a repository and in a directory walked as the settings ask, under eight seeds, and in scratch over 1,000 sequences of up to twelve changes; each case either review found, named; each of 38 rules broken in turn and a test seen failing; a search after an edit through the tools, in a repository, with the default settings.

### O3. One pass for a search after an edit

The search's stale check hands what it found to the index run, which scans and plans again today: 300 ms less at once, with or without O1. It touches `SearchService` and `IndexingService`.

Done (2026-10-29): the stale check (`IndexingService.stale_check`) hands the run (`index_from_check`) the files its scan found, and the run plans once it holds the index. The scan is what the run took again for nothing; the plan is what another run's write since the check makes wrong, so it is made again under the hold: of two searches that checked at once, the second finds the first's work done, and one that waited for another session's first build does not build it twice. The review of O3 and O2 found the scan wrong too in that case: a file made after the check and indexed by another run was taken back out by the run from the check, and one edited after it recorded again with its older stamp, where the scan under the hold had done neither. So the check keeps the index's manifest, read before anything else of the index, which every write that changes the index records anew, and a run that finds another one under its hold scans again: one file read, the usual path keeping the saving. Handing the plan too, trusted while the index's manifest stayed the same, would save the plan too, 250 ms at the median in process at a load of 5 (the index's records read in 77 ms, compared in 177), but it trusts a view of the index taken before the hold for a cost O2 cuts. ### O4. A first index in a pool, streamed, in few writes

Chunking in a pool of processes (ADR 009's step 7, moved here): about 7-10 s to 3-4 s by D12's probe. Streamed: a slice of files chunked, then written, then the next, instead of every chunk held before the first write: the peak from 383 MB to about 150, and what the server holds after it as low, as Python does not hand freed memory back. A whole first build (ADR 009, D12) written in large transactions: about 1.3 s less. Together Sentry's first answer about 6-7 s instead of 12.5. It needs `__main__` that does nothing on import, as a pool's workers start from a forkserver on Linux.

Measured again before it is built (2026-10-29, after O3 and O2, in process, a load of 1.3, two runs): a first index of Sentry by words takes 13.3-15.3 s, chunking 9.2-10.8 of it, 318 writes 3.8-4.1 (10-11 ms each at the median, the search text and FTS5's inserts among them), the scan and the plan 0.3; `evals speed`'s cold first answer through a server is 15.1-15.4 s. The construction to build, in this order of risk:
- **The pool's life**: `concurrent.futures.ProcessPoolExecutor` on a forkserver context, at most four workers and half the cores (D12: four chunked Sentry in 2.7 s, eight in 4.1), made for a run of at least a number of files a probe sets (Sentry's 8,546 gain; algotrading's 1,399, where the pool's first start of 1.2 s eats the gain, may not) and shut down after it, so no idle worker holds memory between runs; small runs and the tests' changing chunkers chunk in process as now.
- **A task is a batch of files**, a few dozen, chunked by a chunker the task builds from a factory the composition root hands down (a function of a module, which pickles by name): no state of a module in the workers.
- **The protocol's pipe kept clean**: a worker's file descriptor 1 is the MCP session's stdout, so the pool's initializer points it at stderr before anything runs; one stray line from a library would break the session. An end-to-end test with a chunker that prints holds it.
- **Streamed**: batches come back in the files' order; the run groups their files into write slices and writes each as it fills, in a worker thread while the pool chunks on, so a first index holds the batches in flight and a slice, not every chunk (the peak D12 measured at 383 MB).
- **Few writes for a whole first build**: where the index is empty, slices of thousands of chunks, as a build that stops keeps nothing anyway and each write costs its own few milliseconds; a run that is not a whole build keeps today's slices, each kept if it stops.
- **`__main__` imports nothing** but under its guard, as a forkserver imports the main module; a cancelled run shuts the pool down with its futures cancelled.
- **Tests**: a first index through the pool gives the chunks and records one in process gives; a run below the threshold makes no pool; a cancelled run leaves no worker behind; what a worker prints reaches stderr only.

Built (2026-10-29) by that construction where measuring it bore it out, and otherwise as the measures drew it; `services/chunking.py` says how a run's batches go, `pools.py` how a pool and its processes live:
- **Processes, as D12 found**: tree-sitter's parse holds the GIL (four threads parsed 4,000 of Sentry's files in 4.1 s where one took 2.5), and 3.14's pool of subinterpreters cannot load tree-sitter, its grammars or pydantic-core.
- **Streamed, in process too**: a run chunks its files a batch of 32 at a time and writes them as they come, in slices of whole files of 256 chunks as before; a slice is written once a file after it has come, so the last write is known as the last. Chunked in process, Sentry's first index peaked at 133-155 MB, its proportional share of memory, against 365-370 MB resident when every chunk waited for the first write.
- **The run's pace is its writes'**, one thread of the server: Sentry's 318 writes took 3.3-3.4 s alone and 4 to 7 s beside a pool, which takes cores and the processor's clock. A pool of four, where they are at most half the cores, as D12 drew it: on Sentry a first index took 5.3 s at the median of four turns in four workers, 5.5 in three and 6.9 in two (11.7-12.2 in the server alone), algotrading 1.5-1.7, 1.6-1.9 and 1.7-1.9 (3.2-3.5), each worker holding about 45 MB while it lives. The first build had two, from turns that a probe's own reader of `/proc`, every 10 ms beside the writes, had slowed; its review's turns had four faster.
- **A pool for a run of 8 MiB of source or more**, its size from the scan's stamps, as an empty `__init__.py` is a file and no work: of Sentry's first files a pool of two (the first build's) indexed 4 MiB in 1.7-1.8 s where the server alone took 1.6-2.0, and 8 MiB in 4.7-4.9 s against 5.6-6.6. Algotrading's 13.5 MB and Sentry's 66.8 take it; the pinned corpora, 1.3 MB at most, and nearly every edit do not. A pool starts in about 0.2 s, where D12 measured 1.2.
- **A task is a batch and the chunker itself**, not a factory: the chunker pickles as its classes in 296 bytes. A factory in the composition root, as drawn, would have made each worker import `app` and with it `mcp`: 0.85 s and 93 MB a worker at every pool's start. Batches of 32 files chunked Sentry fastest (four workers: 5.0 s, against 5.4-6.0 in batches of 8, 16 or 64); a worker has two in hand, taken back in the files' order; unpickling every chunk in the server costs 0.3 s in all.
- **The console script's module, not `__main__`'s guard**: multiprocessing never imports a package's `__main__` again in a child, so `python -m` needed nothing; the console script that `uvx` runs is imported again in the forkserver, and it imported `semantic_code_mcp.cli`, so the forkserver took 0.6 s at its first start and held 94 MB resident for the rest of the session. The console script now names `semantic_code_mcp.__main__:main`, which imports the server only when it runs: through the real script, after a first index of Sentry, the forkserver holds 19 MB and multiprocessing's resource tracker 16.
- **The protocol's stream is the SDK's to keep**, not the construction's premise, that a worker's fd 1 is the session's: while it serves, mcp's stdio server (2.3) points the server's fd 0 at the null device and fd 1 at stderr and keeps the protocol on a descriptor of its own, which children do not inherit, so a pool's processes inherit no part of the session (its review read each one's descriptors in `/proc`). Each worker's initializer points its fd 1 at stderr all the same, whatever the server's is, and logs as the server does, as structlog's default prints to stdout, a line for every file at the debug level; its test runs a pool in a process of its own, not a server, and reads that process's stdout.
- **Few writes for a whole first build: not built.** Slices of 256, 1,024, 4,096, 16,384 or all 87,694 chunks wrote Sentry's whole build in 2.9-4.1 s, the same within the spread, as ADR 009's step 6 found: the writes cost their rows, not their count.
- **A cancelled run** leaves the block its batches live in, which shuts the pool down off the event loop, the batches not begun cancelled and those begun finished; its test sees no process of the pool left once the cancellation lands.
- **Workers end with the server**: a worker waits on its call queue, whose ends each worker holds too, so a server killed mid-run (SIGKILL, the OOM killer, a SIGTERM it does not handle) left its two workers, the forkserver and the resource tracker running, still there 80 s later in its review's probe; a thread of each worker's own now waits on the server's sentinel and ends the worker with it, and the other two end once the workers have. Its test kills a run stopped in its first write and waits for every process of its to let go of its stdout and stderr.
- **A system that cannot start a pool**, without working semaphores or the Unix sockets its forkserver needs, has every run chunked in the server, said once in the log and not asked again that session; the pool is started as it is opened, its first process with it, so such a system says so there. Its tests hand the run an opener that refuses, and start one in a process whose forkserver cannot start, the resource tracker running and the interpreter to start missing. A worker that dies mid-run fails the call (`BrokenProcessPool`), and the next search builds again.
- **The pool is a part**, `pools.py`, beside `watching/`, and an import-linter contract keeps `multiprocessing` and `concurrent` in it; `Chunking` takes its opener, so a test hands it a pool that runs each task as it is handed out and sees a run hand out its last batches only once it has written others. A gate, `scripts/check_entry_point.py`, refuses a console script whose module, as `[project.scripts]` names it, imports anything of the server or of `mcp` as it is imported; a test killing a run kills its session of processes whole after, so a failure leaves none.
- **`evals speed` reads the memory of the server and every process it starts**, by each one's proportional share, summed, every 50 ms while the server works: it read the server's own process alone, which leaves out the pool, the forkserver and the tracker.

## Alternatives Considered

- **A stale check from git** (`status` and `diff` from a recorded commit): about 40 ms, turned down in ADR 009 for what git shows only with care; O1 sees every change, tracked or not.
- **A stale check cached for some seconds**: an agent that edits and searches at once would meet the old index.
- **Larger slices for every run**: a run that is not a first build keeps each slice it wrote when cancelled; only the whole build gains nothing from small ones.
- **A faster `mcp` import**: not ours to change.
- **Threads, or 3.14's subinterpreters, for chunking**: tree-sitter's parse holds the GIL, and neither tree-sitter, its grammars nor pydantic-core load in a subinterpreter (O4).
- **A follower of their own for macOS and Windows**, another `ProjectFiles` as the plan drew it: each would have written the follower's rules again for a tree watched whole; a tree's changes told as inotify's keep one follower, tested alike on the three systems (O1).
- **`FSEventStreamFlushSync` as macOS's barrier**: CI found it none; a mark made and waited for is (O1).
- **Two workers**: about 1.5 s slower on Sentry than four, as two chunk slower than the writes go, for 90 MB less at the peak; the first build had them from turns a probe of its own had slowed (O4).

## Consequences

- A warm search on a large repository costs what its search does, not what its scan does; a search after an edit, what the edit's file costs.
- A first answer on Sentry takes about two thirds as long, 10 s, and the server's processes peak at 300 MB against 345 and hold about 135 MB after against 220; a first index of much source takes up to four more cores for its seconds.
- O1 adds a part with a life of its own (a watcher per project, started at its first look and closed with the server's session: an inotify instance on Linux; on macOS a stream per tree, its queue's thread and a temporary directory of marks; on Windows a handle per tree) and no dependency: its calls go through `ctypes`, which an import-linter contract keeps in `watching/`, and ty checks every platform's code wherever it runs. Each server on Linux takes a watch per directory from the user's limit, which editors share, until one daemon per user (`TODO.md`) holds one for every session; on Windows a directory holding one watched cannot be moved meanwhile.
