## Context

The first search of a repository waits for its whole index inside one tool call: 733 s on the owner's algotrading (1,399 files, 19,432 chunks), about an hour on Sentry (8,546 files, 87,694 chunks). Split by phase on algotrading, the model takes about 95% of it: finding the files takes 0.6 s, chunking about 11 s, tokenizing 6.5 s (all under load), and 2.85 million tokens through a six-layer transformer the rest. A rate was measured and targeted ("a full index over 20 chunks a second", which allows 15 minutes on 19k chunks), never the wait; stage 7 raised the rate by percents. And 26% of chunks run past the model's 256 tokens, so 42% of the code's text never reaches it.

A warm search pays too: before every search the server finds the files and compares them with the index, 1.13 s on Sentry, of which git takes 0.04 s and Python's handling of 8,546 paths most of the rest (D4). The pinned corpora have 32 to 133 files, so no target saw it.

How the product is used, as the owner set it (2026-10-27, 2026-10-28): any developer, first the repositories one works in often (worktrees, branch switches, several sessions at once), then first contact with a stranger's large repository; any agent, Claude Code first; code never leaves the machine; no hidden load on the user's CPU; dependencies' code last, indexed in turn; the word index whole, meaning in parts; the product keeps its name.

Whether the tool is needed, and what part of it: 180 sessions of Claude Code headless (ADR 008, pilot 8):

## Decision

### D1. Words by default, an exact name first

`search_code` answers from the keyword channel: BM25 over each chunk's search text (its content, its name, the words of its identifiers, its parent's words). The model is not loaded for it. Hits keep up to 50 lines (ADR 008, pilot 7).

A query that is a chunk's name, its case and the blanks around it aside (`name_asked`), puts the chunks of that name first, then the rest by BM25; a qualified name (`Stack.push`) is read as a parent and a name. Today the name only keeps its chunk past the floors; by words alone a bare name ranks under the chunks that use it most (click's 89: chunk MRR 0.83 with MiniLM, 0.68 by words). The rule is held to ADR 006's criterion on the bare names.

### D2. Meaning on request

`search_code` takes `by_meaning`, false by default; a setting gives its default for a user who wants meaning always. With it, the search fuses both channels as today. The model is MiniLM, as today: the static model ranks below words alone where an agent asks most, on bare names, in two corpora of three (Context).

- A hit with a vector is held to the similarity floors as today; one without (its file not yet embedded, D3) came by words and stays by their rules.
- `similarity` leaves the hit: a hit by words has none, and a number on two scales misleads; the order is the ranking.
- The tool's description says: the default matches the words of code, so write the identifiers and terms code would use and search again with others on a miss; set `by_meaning` for behaviour described without the code's words, after a search by words missed; on a repository not yet embedded it starts the embedding and answers from what is there. Pilot 8's agents wrote queries in code's words unprompted; the wording is settled by agents (step 8).
- The model's libraries stay in the base install; its weights come with the first search by meaning.

### D3. The word index whole, meaning in parts

- **Words.** A call that finds the word index missing or stale builds it whole before it answers: 2.6 s on algotrading, 13.5 to 19 s on Sentry. The run takes the project's index lock before it looks for files, so a second session finding the lock held waits, checks again and reads; two sessions never chunk one repository twice. The wait has no limit and reports that another session builds the index: today's 60 s (`WRITE_LOCK_TIMEOUT_SECONDS`) is shorter than Sentry's build under load, where chunking ran about five times its idle time, and the lock is a file lock, freed when its holder's process dies. Parts would save about 13 s once per large repository, and a 733 s run completed inside one call (ADR 008).
- **Vectors.** Embedded by D6 in parts, in this order: files changed in the working tree and the last commits, the directory the search names, the rest of the source, documentation, tests. Each part is written as a unit; a search by meaning fuses the vectors there are.
- **Coverage.** An answer by meaning says what share of the project's chunks has vectors and, until it is all, that the rest came by words alone, so an agent knows what meaning did not see. An answer by words covers the whole index and says nothing more.

### D4. A lean stale check

Every search first finds what changed: discovery lists the files, and the plan compares them with the index's records. On Sentry `index_status` took 1.13 s at the median (2026-10-28, idle), of which discovery 0.79 s, the store's records and chunk paths 0.09 s and the plan 0.01 s. Discovery's time is Python's, not the disk's: git lists the files in 0.04 s, and the rest went to 637,545 calls of `fnmatchcase` (every ignore pattern against every part of every path), to `pathlib`, and to a `realpath` of every file. It keeps its design and is made lean: the ignore patterns joined into one expression of each kind, a directory checked once for all its files, one `lstat` a file, a path resolved whole only where it is a symlink; the walk does not descend into a symlinked directory, and where git lists the tracked files of a directory a symlink has since replaced, that directory is resolved once for all of them. A probe of that found the same 8,546 files in 111 ms. Built (step 3), discovery takes 0.14 s, and through the server `index_status` takes 0.30 s at the median on an idle machine (0.32 to 0.53 s in a review's runs beside other work) instead of 1.13 s, and a warm search 0.44 s instead of 1.18 s; the index stays the one record of what changed, and nothing new is recorded. What is left is the store's reads (LanceDB's records 40 ms, its chunks' paths 55 ms, which a store writing in one transaction does without) the plan's 40 to 80 ms, most of it hashing 17,000 `Path`s, which discovery's old sort by `Path` paid before, and about 100 ms inside the server nobody has attributed.

### D5. Off-topic questions

Without vectors no floor holds back an off-topic hit. Agents were not hurt by that (pilot 8's words-only arm, no floor, 30 of 30 on both corpora), so no rule is built now: `evals quality` reports the off-topic results of each mode, and a rule comes when an agents' run shows the harm.

### D6. Meaning in the background, in a child process

- **A process, not threads.** onnxruntime's own pool does the work, and Python sets no priority on it; a child process takes the lowest priority the platform gives a process (`SCHED_IDLE` on Linux, nice 19 on macOS, `IDLE_PRIORITY_CLASS` on Windows, all from the standard library) and runs the model on two threads, which embed 23 chunks a second against 27 on all of this machine's 16 (2026-10-28): onnxruntime's threads gain little on this model. The query's vector is embedded in the server, at the user's priority, the model loaded there on the first search by meaning as today, and before the child starts, so two processes never fetch its weights at once. A session with meaning on so holds the model twice, the server (569-725 MB resident in `evals/baseline/speed.json` of `c63d4a2`) and the child (789-898 MB at its peak); a query served by an idle child would stall whenever anything else wants the CPU.
- **One child per server**, embedding the projects that asked for meaning one at a time. Before a project it takes the project's embedding lock without waiting; held, it leaves the project to the session holding it, whose vectors this server reads as they land (ADR 007, D7), and tries again after.
- **Owned by the registry.** The registry starts the child on the first search by meaning and stops it when its lifespan ends; the child also stops when the pipe from its parent closes. So it dies with its session: no load once the user closes the agent, and the next session's first search by meaning resumes from the vectors written. At the lowest priority its rate on a busy machine has no floor, so `index_status` reports the vectors' share and the rate. Each part is written in one transaction (SQLite) or under the write lock (LanceDB).
- **Vectors by content, per machine.** A cache keyed by the model's identity and the digest of the text embedded, a SQLite file per model under the cache directory: before embedding a part the child takes what the cache holds, so worktrees, clones and branch switches embed only what is new (six worktrees of algotrading hold 23,273 distinct chunks among 81,682). The cache is only a cache: each project's store keeps its own vectors, so the sweep of unused indexes drops cached vectors no part has used within its period. A vector is 1.5 KB.
- Whether the model gets each chunk's first 64 tokens, three to four times cheaper and as good fused on the Fable reviewer's probe, is settled on the harness.

### D7. The index's identity, split

`IndexIdentity` holds the model's name, its revision, the embedder's version and the chunker's version (`domain/models.py`), so with words the default, a change of a model setting never used would build the word index again. It splits: the word index is identified by the chunker's version, the search text's version and the store's kind, which name its directory; the vectors by the model's name, revision and the embedder's version, kept apart by that identity inside the store, so a change of model embeds again without chunking again. The vectors of a model no longer used stay in a live index until it is built again; a change of model is rare. It comes with step 6, as it rests on chunks without vectors, the contract's change that words by default make. A chunk's id is a digest of its path, its occurrence in the file and its text (`chunkers/base.py`), so a vector stored under the model's identity and the chunk's id is that text's vector for as long as both live: the store keeps vectors apart from the chunks, by those two keys. A write of words keeps the vectors of the chunk ids it keeps and drops those of the ids it drops, which takes the place of today's reuse through `stored_vectors`; a forced run drops the current model's vectors; vectors of another width than a model's new ones (a model replaced under a name nothing pins) drop that model's vectors alone, the words untouched. The directory is named by the chunker's version and the store's layout, whose schema version covers the search text; the manifest records them, and `index_status` the share of chunks each model has vectors for. This changes the domain model and the storage schema, which AGENTS.md asks about first; the owner left the technical construction to the authors and the Fable reviewer (2026-10-28).

### D8. Stores behind one contract: SQLite by default, LanceDB as an option, more to come

- The contract (ADR 007, D1, D2) in the index's own terms: the manifest, the files' records, a part written as a unit, chunks without vectors, vectors added to stored chunks by model identity, the candidates of words and of meaning read from one state, the counts coverage needs.
- One suite of tests holds the contract over a store factory, run on every store; a store's own behaviour is tested apart. A new store is a module, an optional extra of the package with its libraries, and the suite passing; import-linter keeps stores from importing one another.
- A setting picks the store (`SEMANTIC_CODE_MCP_INDEX_STORE`); its kind is part of the index's directory name, so stores never meet one another's files, and the sweep of unused indexes removes any kind. Each store is built on the directory the composition root hands it, and its class names its layout (kind and schema version); LanceDB's directories take the kind too, so a LanceDB index is built again once, as the identity split (D7) would make every index anyway.
- SQLite is the default: one database file in WAL mode; a part's write in one transaction; FTS5 over the search text (`porter unicode61`, no copy of the text), a query's tokens each quoted and joined by OR, so the question is never read as FTS5's syntax; vectors as float32 blobs beside each chunk, searched by a matrix of unit vectors the store holds between searches. As built (step 5), the search's read transaction checks the matrix against the chunks' state, the last row id the table gave (AUTOINCREMENT gives none twice) and its count of chunks, so no generation or log of changes is kept; a later state refreshes the matrix by rows, the deleted dropped and those past the old last row id read. A scope's chunks come from an index of (path, kind, language) rather than the chunks' wide rows, a glob is matched once a file against the files' records, and the keyword channel ranks row ids before it reads any chunk's columns: reading them for every chunk a question's words matched took 181 ms of a 203 ms search at 88k chunks. The product with the query runs on numpy's own loop, not OpenBLAS, whose threads spun on every core after it and slowed the next query from 38 to 73 ms.
- Probed at Sentry's size (87,694 chunks, both stores filled from the same rows, each in a fresh process in ABBA turns, the machine at a load of 2.6 to 4.1), SQLite against LanceDB at the median: a warm search 53 ms against 61 (p95 100 against 75), narrowed to functions and methods outside the tests 110 against 121, the search after another session's edit of one file 130 against 68 (the matrix refreshed), the status's reads 25 against 90, an edit's write 18 against 152 (LanceDB's compaction 2.7 s at a store's first), the first search 427 against 94 (the matrix read whole); the process held 312 to 332 MB at the end against 1,269 to 1,358, its peak 676 against 1,395 to 1,482.
- The contract as step 6 changes it: `write(update)` of files, chunks and removals, without vectors; `chunks_without_vectors(model)`; `add_vectors(model, chunk ids, vectors)`, which skips ids the index no longer holds; `chunks_named(name, parent, scope)` for D1's exact name; `search_words(query, limit)`; `search(model, query vector, query, per channel)`, both channels read from one state; `counts(model)` with the vectors' share. SQLite keeps the vectors in a table of their own keyed by (model, chunk id), its rows given by AUTOINCREMENT, so a matrix held per model is checked against that table's state as step 5 built it, the database's id included. LanceDB keeps a table of vectors per model holding, beside each vector, the chunk's id and the columns a scope filters by (path, kind, language), as its vector search filters before it cuts and cannot join; a model's table goes whole when its width changes. The indexing service writes words alone; a search by meaning first embeds `chunks_without_vectors(model)` inside the call, as today, adding each slice's vectors as it goes, so a cancelled call keeps the slices it added.
- LanceDB is the extra `semantic-code-mcp[lancedb]`: today's store, with chunks without vectors added and its upkeep kept to itself. It stays because users already keep their vectors in it, and a second store shows the contract holds and how one is added.

### D9. Targets

They replace those of `.claude/rules/mcp-server.md` that this changes, each held by `evals speed`:
- the first answer on a repository never indexed: within 10 s at 20k chunks and 60 s at 100k (measured idle on SQLite: 2.6 s and 19.0 s);
- the stale check of a search: within 300 ms at 100k chunks (Sentry: 1.13 s before step 3, 0.30 to 0.40 s after it; not yet met through the server, where the store's reads, the plan and about 100 ms unattributed remain);
- a warm search by words: within 500 ms at p95 at 100k chunks (FTS5: 265 ms at its slowest idle, 385 ms under load), what an agent's turn of seconds does not notice, in place of 80 ms at the median;
- a search after an edit of one file, and `index_status`, as today;
- embedding in the background: one child process, two threads, the lowest priority; "a full index over 20 chunks a second" goes;
- the server's memory without meaning, and the server's and the child's with it: set from the first measurement of steps 6 and 9.

### D10. Measurement

- `evals speed` reports the first answer on a repository never indexed, the stale check and a warm search on a corpus of Sentry's size (`--corpus-file`), and the memory of the server and the child with meaning on; a probe splits a phase where a change needs it.
- `evals quality` reports words and meaning apart: code, documentation, bare names, off-topic results.
- `evals agents` takes ADR 008's open fixes, those pilot 8 already ran (arms rotated, project settings shut out, no API key, a stop on an error result or a server down, every stream kept) among them, and arms of own tools, words, and words with `by_meaning` offered.

### D11. ADR 007's turn

ADR 007 turned SQLite down for its keyword channel: 96 ms at the median at 100k chunks against LanceDB's 7, and a fast form that ranks worse. Against an agent's turn of seconds that cost does not show, and the target moves (D9); with words the default channel, SQLite's exact full-text index after every write, its chunks without vectors and an install 422 MB smaller decide. ADR 007's contract, directory and suite (D1 to D5) become this decision's steps; the identity's split and the vector cache follow them.

### D12. A faster first index and search

A first index of Sentry by words, idle, in a probe of 2026-10-28: discovery 0.70 s, chunking 9.6 s, search text 0.9 s, the chunks and FTS5 written 2.3 s, about 13.5 s in all (step 0's 19 s had FTS5 at 6.4 s, written beside other work). Tree-sitter's parse, in C, is 7.8 s of the chunking, and it holds the GIL, so only processes cut it: a pool of four chunked Sentry in 2.7 s, eight in 4.1 s (this processor has four performance and eight efficiency cores, and the parent unpacks every chunk alone); the first pool of a process starts in 1.2 s, the next at once (Python 3.14 starts them from a forkserver on Linux). FTS5 without its own copy of the text (`content=''`, `contentless_delete=1`) wrote in 2.0 s and 162 MB against 288 MB, and without a journal or waiting for the disk (`synchronous=OFF`) in 1.7 s.

- **Discovery made lean** (D4): 0.70 s to 0.14 s.
- **FTS5 contentless**; a first build written to a new database under a temporary name, without a journal, and renamed into place when whole, so a crash leaves only a file to delete: 2.3 s to 1.7 s. FTS5 contentless and the empty database made whole under a temporary name came with step 5; the first build without a journal comes with step 6: it hides a first index's writes until its end, which fits a first index of words alone, seconds long, not today's, which embeds for minutes and keeps what a cancelled first index wrote.
- **Chunking in a pool of processes**, at most four and half the cores, for a run with files enough to pay its start (step 7 sets the bound), the search text made in the parent, as made in the pool and sent back it took four workers 5.7 s (a review's probe): chunking 9.6 s to about 4.2 s with the start, 5.1 s with the search text. A process started by forkserver or spawn imports the main module again, so the server's entry point allows it.
- **Together**: Sentry's first index by words from about 13.5 s to about 7 s; algotrading's stays about 2.4 s, the pool's start eating what it saves there.
- **Each search**: the lean stale check (D4), and a query's words that most chunks hold (half of them, as the first candidate) left out of it: they barely move BM25 and make FTS5 score nearly every chunk; held to ADR 006's criterion, which kept stop words in the index (stage 6). ADR 007's spike left every stop word out of the query and failed it (code 37.09 to 35.33 in reciprocal-rank sum, documentation 12.0 to 9.5), and words of more than 5% of the chunks left out took 33 ms at the median against 96; the bound tried here is far looser.
- **Not lower**: FTS5 never prunes weak candidates, which gives LanceDB its 9 ms; that on SQLite needs an index of our own in memory, and bm25s built slower than FTS5 (43 s on Sentry under load). Below about 150 ms an agent's turn of seconds does not notice.

### Outside this decision

## Alternatives Considered

- **A faster transformer** (int8, a 64-token head, threads): two to four times, not a hundred; Sentry stays at minutes on every core.
- **Vectors in the background by default** (the Fable reviewer's second tier): agents showed no gain from them, and they cost hours of a capped CPU on a large repository.
- **A static model as the meaning** (potion-code-16M-v2): about a hundred times the transformer's speed, so no background and no parts; but against words alone it is better in 10 cells of 15, equal in 1 and worse in 4 (fd's bare names and held-out code, this repository's documentation and bare names), and MiniLM leads it in 13 and ties in one. Kept as the way out if step 9 shows the transformer's cost cannot be borne.
- **Staleness from git** (`status` and `diff` from a commit the manifest records, as this decision first had it): about 40 ms on Sentry against the lean check's 0.3 to 0.4 s, but it records a commit and a digest of the settings, and must catch what git shows only with care: a renamed file's old path, an untracked directory's files, a deleted untracked file, a change of the excludes (the Fable reviewer's probe). Later, if a repository larger than Sentry needs it.
- **Words in parts too**: parts, a background run of words and coverage by part, to save 13 s once per large repository; the owner chose the word index whole.
- **Threads at the lowest priority**: the work runs on onnxruntime's pool, whose priority Python cannot set, and the model would stay in every server.
- **A child per repository**: a session with meaning on in three repositories would load three models; one child takes them in turn.
- **A rule against off-topic hits now**: no agent has shown the harm, and ADR 006's criterion (fewer than 10 more off-topic results) is unlikely to pass on the near questions at 140 against 1 to 14.
- **A remote embedding API**: the code leaves the machine.
- **Indexes shared across a team** (Cursor's): needs a server; vectors kept by content give the same within one machine.
- **Words alone, meaning dropped**: the harness shows its niche, questions without the code's words (fd's code 0.53 against 0.16).
- **LanceDB by default**: 422 MB more for every user; rows not yet folded into its full-text index score on another scale; chunks without vectors need a schema change there too.
- **A daemon per user**: one embedder and one watcher for every session, at the cost of a process's life on three platforms; later, if one child per server falls short.

## Consequences

- A first search costs seconds on any repository up to Sentry's size (2.6 s on algotrading, 13.5 to 19 s on Sentry; about 2.4 s and 6.5 s after D12), and a warm search on Sentry stops spending a second finding files.
- What it costs a user by words: a first index of one core for 2.6 s on algotrading and 13.5 to 19 s on Sentry (four cores for seconds after D12); each search 0.3 to 0.4 s of stale check on Sentry and 15 or 105 ms of FTS5 at the median; an edit about 150 ms; the index on disk 48 MB and 288 MB in the probes, 162 MB on Sentry with FTS5 contentless; nothing in the background. The server's memory without the model is not yet measured; with it today, 569-725 MB.
- What it costs with meaning: about 1.5 GB while the vectors are made (the server 569-725 MB, the child 789-898 MB at its peak); two of this machine's 16 threads at the lowest priority, at 23 chunks a second when nothing else wants them: about 14 min on algotrading and 63 min on Sentry, 4 and 19 min with the 64-token head (76 a second); 1.5 KB a vector (29 MB and 130 MB), the cache's copy beside them; the model's weights, about 90 MB, fetched once.
- By default the harness's questions rank worse: code by 0.14 chunk MRR in every corpus, documentation by 0.09 to 0.19, questions with none of the answer's words by 0.15 to 0.40, held-out code on click from 0.80 to 0.53 and on this repository from 0.87 to 0.62, bare names on click from 0.83 to 0.68 until the exact-name rule. Agents made up for it in pilot 8 by searching again, and meaning is one parameter away.
- The model is in a server only after a search by meaning there; the child that embeds lives as long as its session.
- Every user's index is built again once, in a new directory; without meaning that takes seconds.
- LanceDB's upkeep, its pin at 0.30.2 and pylance move into an optional store; the default store has neither, and the install is 190 MB against 616 with the extra (measured 2026-10-28).
- `search_code`'s input gains `by_meaning`, its hits lose `similarity`, its answer by meaning gains coverage; the descriptions, README, the skill and the server's instructions say plainly that the default matches words and meaning is a parameter. The product keeps its name.
- Stage 7's work on the model's speed now serves meaning alone; TODO's "LanceDB index tuning" serves the LanceDB store alone.
