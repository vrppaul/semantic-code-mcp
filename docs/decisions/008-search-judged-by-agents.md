# 008: Search judged by agents

**Status**: accepted; `evals agents` built (2026-10-27), its review's list done (2026-10-28, ADR 009 step 10)
**Date**: 2026-10-27
**Continues**: 006 (D12, the harness), 007 (step 1)

## Context

`evals quality` ranks chunks: it says where a question's answer lands among the hits of `search_code`. It cannot say whether an agent that has the server finds its answer sooner, or at all, than one with Read, Grep and Glob alone, and that is what the server is for. Several changes ahead are judged by nothing else: compact hits change what an agent reads after a search, not the ranking; the skill changes which tool an agent picks and how it asks (ADR 006 lists it as never run with and without); and a store or a model could rank alike and still cost an agent more turns. The owner asked for search judged by agents themselves (2026-10-27), run on his subscription.

## Decision

### D1. Tasks with keys

The harness's chosen questions, code and documentation, each asked as a task: find what does this in the repository, and end the reply with one line of JSON naming the file from the repository's root and the function, method, class or section. The answer is scored against the question's keys (`evals/corpora/*.toml`) without a judge, through the chunks of the file it names as the server chunks it: its name, bare, qualified by its class or its module, written as a call or as a heading with its marks, is read as the chunks of that file it names, as written or, where no chunk has that name, without a note in parentheses after it (`Event.group (setter)`; a heading may hold parentheses of its own), and those are matched with the keys as `evals quality` matches a hit, by the parent where a key names one. A qualifier no chunk of the name sits in is read as the module's path, so `click.termui.progressbar` names the top-level `progressbar`, and `Choice.convert` never passes a key of `_NumberRangeBase.convert`. The file is right when a key names it; the answer is right when it names a keyed chunk, and counts as right, reported apart, when it names a member of a keyed chunk or the chunk a keyed one sits in, the rule pilots 8 and 9 used, now for bare and qualified names alike. Three kinds of answer go to a judge, as the harness pools its keys: a bare name of several parents that the keys tell apart, a name no chunk of its file has (a class the file lacks, a file the server does not chunk), and a chunk no key names. A judge's verdict goes into the question's judged answers (`[[queries.judged]]`: the path and symbol as the agent wrote them, right or wrong, and why), read before the chunks, as a key could not hold an answer no chunk names, nor one judged wrong; then the kept run is scored again (D6). The held-out questions stay held out.

### D2. Arms

Each task runs in each arm with the same prompt, which names no tool. An arm is named by what the agent is given, and where it has the server, by the server's setting (ADR 009, D10):
- **own_tools**: Claude Code's Read, Grep and Glob, and its shell for reading (`rg`, `grep`, `find`, `ls`, `cat`, `head`, `tail`, `sed -n`, `wc`, `git grep`, `git log`);
- **words**, **words_and_meaning**: the same, and this server's `search_code` and `index_status`, the server set to that search mode (`SEMANTIC_CODE_MCP_SEARCH_MODE`); a mode the server gains is an arm;
- **with search and the skill**: the skill loaded from the repository (`--plugin-dir`). Not built: pilot 2 saw the skill loaded and unused, and with the search in the prompt the agent searched unprompted (pilots 5 and 6).

A run that names no arm asks own_tools and words, the server as it ships. No arm edits, fetches from the web or starts subagents, so a session's cost is its own.

### D3. Sessions alike, and apart from the owner's own

Each session is Claude Code headless (`claude -p`, `--output-format stream-json`), started in the corpus's checkout. It runs in a home of its own, whose config directory holds only a link to the owner's login, so none of the owner's own instructions, memory, hooks, MCP servers or shell setup reach it (Claude Code still fills the directory with the account's synced skills and plugins): his `CLAUDE.md` asks an agent to wait for his word before acting, which would end a task before it starts, and his shell's aliases (`ls` as `eza`, with colours, and zsh's globbing) reached pilot 9's sessions through Claude Code's snapshot of the user's shell. The login is the file Claude Code keeps on Linux; on macOS it is in the keychain under a name a config directory of its own does not find, so the harness runs on Linux. `--bare` would isolate a session too, but never reads a login, only an API key. The corpus's project and local settings are left out (`--setting-sources user`): by Claude Code's documentation that leaves out its `.claude/settings.json` and hooks, its rules and its project skills and commands, and by the Agent SDK's, which names the same sources, its `CLAUDE.md`; its `AGENTS.md` comes through a built-in plugin that no documented flag governs, loaded where no `CLAUDE.md` is found. So the corpus's own instructions stay out, though real users have them: they may name tools, and would reach every arm alike. Of the caller's environment only what Claude Code needs to run on the login reaches a session (`PATH`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `TMPDIR`, the home its own): a headless session always uses an API key it finds in its environment, and the caller's own settings change how the agent works. A run stops at the first session whose init names it billed to anything but the login. The arm's MCP config is the only one (`--strict-mcp-config`). The server is this environment's (`python -m semantic_code_mcp` on the harness's own interpreter), in the owner's home, as a user's server runs in the user's, the model's weights cached there; its index kept between runs under the checkouts' cache (`indexes/<corpus>-<commit>`), as a large corpus's takes an hour, and brought up to date before the first session in every mode an arm searches in: by words an index run, by meaning a search, which first embeds every chunk without its vector, an hour on Sentry; so no session pays a first index. A run is started under a memory cap, as `evals quality` is.

### D4. What a session is scored by

How it ended: answered; closed without an answer; timed out, at 600 s; failed, by no init, an error result, an exit other than 0 or no result; billed to anything but the login; or its arm's server not connected, the last two read off its init. Whether its file and its answer are right (D1); its turns; its prompt, every token it sent, read from the cache, written to it or neither, as what one session reads from the cache another wrote; its output tokens; its tool calls, by tool; its time; the model and Claude Code's version its init names, the alias asked for kept beside them. The means hold the sessions that closed, answered or not; the others are counted apart, and each comparison says how many it left out (D5). A failed session stops the run, as do one billed elsewhere and one whose arm's server did not connect: each measures something else, and a lapsed login or a spent limit would otherwise read as cheap wrong sessions; their outcomes keep them out of the means when a stopped run is scored again. Claude Code's cost is summed for the run, to watch the subscription, and never compared: on Sonnet it fits $2 a million input, $0.10 cache read, $4 cache write (1 h) and $10 output, so cache writes are 64-94% of a session's cost, and how much a session writes the order of the sessions decides.

### D5. Noise

An agent's path through a task varies from session to session, and from task to task far more, so each task runs several times in each arm (`--repeats`), the arms taking turns to go first question by question and repeat by repeat, and two arms are compared on the questions both asked: each question's figure is the mean of its sessions in an arm, and the difference is the mean over the questions with its 95% interval by a paired bootstrap (10,000 resamples, seeded, so a run scored again gives the same), and on how many questions it went down, stayed and went up, in turns and in prompt tokens, with how many sessions of the two arms did not close: leaving out an arm's slowest sessions flatters it, and a question an arm timed out on in every repeat leaves the comparison. A difference counts where its interval leaves out zero. How many repeats a question needs is settled by asking algotrading's fifteen three times, a run that waits for the owner's word; pilots 8 and 9 asked each question twice.

### D6. Where it lives

`evals agents` beside `quality` and `speed`: `evals/agents.py` runs the sessions, `evals/agent_answers.py` scores the answers, `evals/agent_summary.py` sums the arms and compares them. A run names its corpora, one at least (`--corpus`, or `--corpus-file` for one kept outside the repository, as a private repository's questions are), as the pinned corpora are small enough to grep and spent about 130 sessions showing nothing, and never two files of one corpus, as it keeps and scores sessions by the corpus's name; then its arms, its repeats and its model. It prints each session as it ends, then each arm's sums, every arm against each named before it, and the answers to judge. Each run keeps under its name, its start in UTC, in `~/.cache/semantic-code-mcp-evals/agents/runs/`, outside the repository, as its streams hold a private corpus's code: what it asked (`run.json`), each session as it ends (`sessions.jsonl`, so a run stopped midway keeps what it spent), each session's stream, and its report. `evals rescore <run>` scores a kept run again by its corpora's keys and judged answers as they are now, a stopped one too. It keeps no baseline: its sessions hold the questions of private corpora. It measures the product, so it is code of the repository, tested where it reads a session, scores an answer and sums the arms (`tests/unit/test_evals_agent*.py`), and where it runs, Claude Code faked by a script on PATH (`tests/data/fake_claude.py`): the sessions kept, their order, their flags and environment, a stop, the rescoring, and an arm's index brought up to date by meaning (`tests/integration/`, `tests/e2e/test_evals_agents.py`).

- **How many repeats (D5)**: algotrading's fifteen asked three times, with the owner's word for the run.

## Alternatives Considered

- **The owner's own configuration.** His instructions, hooks and plugins would reach every session, and his `CLAUDE.md` asks the agent to wait for his word.
- **`--bare` with an API key.** Isolates the session with no link to a login, but bills an API account; the owner chose his subscription.
- **Coding tasks graded by their tests (SWE-bench's way).** Nearer to real work, but each needs a task, a failing test and a sandbox, and costs many times more per session; locating code is where the server acts, and the harness's keys already exist.
- **An LLM judging every answer.** The keys judge most answers for free; a judge reads only the answers outside them, as the harness's pooling does.

## Consequences

- A change of the server can be shown to help, or not, an agent's work, not only the rank of a chunk.
- Each run spends the owner's subscription; the pilot sets its size.
- Models know click and fd from their training and may answer from memory, which favours the own-tools arm alike in both; this repository and a corpus newer than the models' training show the difference cleaner, and the results are reported by corpus.
- The keys were pooled from this server's own hits, so an agent that finds a right answer by other means scores as wrong until it is judged; answers outside the keys are listed in every run.
